# 本地 Docker Desktop 演示版最终执行计划

日期：2026-09-30。版本：v2。状态：用户已批准并完成执行（P1–P7）。
逐项执行状态与命令证据见同目录 execution-log.md。

## 1. 交付目标

在当前 Windows 电脑的 Docker Desktop 中运行完整应用：虚构业务数据、真实后端功能、真实模型调用。日常从项目根目录运行 .\scripts\start.ps1 即可启动，通过一个本机工作台地址访问。

业务功能包括订单/物流查询、真实向量政策检索、工单创建与查询、人工审批、演示订单退款入账、库存建议与预留、审计追踪。聊天继续使用本地 .env 中配置的 DeepSeek，embedding 继续独立使用 SiliconFlow Qwen/Qwen3-Embedding-0.6B，维度 1024。不为了部署替换模型、Key 或基础 URL。

所有业务对象都是合成数据。支付、电商、物流和 WMS 外部接口不接入。本次交付仅本机访问，不购买服务器、域名或配置公网入口。

## 2. 审查结论及修正

| 原计划问题 | 最终处理 |
|---|---|
| “真实业务闭环”含义宽泛 | 按下表定义每个功能的实际终点；界面和验收使用相同口径 |
| 退款目前只校验，未改订单金额 | 新增本地演示退款执行模式：事务更新虚构订单退款累计金额并写退款记录；旧模拟结果保持可读 |
| 订单 status 只有支付/物流状态 | 不把 REFUNDED 塞进原状态枚举；部分/全额退款进度由金额计算或独立字段表达 |
| 库存实现只有预留和到期释放 | 首期明确交付到该终点，不把预留结果称为已完成仓库间移动 |
| 每日额度替代原累计额度会改变旧保护 | 保留 lifetime 计数行为；仅专用 local-demo 配置显式选择 daily；历史累计计数不清零 |
| 四项服务映射到宿主机导致端口冲突 | 演示配置只发布 Web 的一个回环端口；其余服务只在 Docker 网络内通信 |
| “一键启动”仍可能每次编译 | 构建与运行分开：已有版本只启动；首次缺镜像时构建或导入，源码变化后显式更新 |
| 打包方案只有源码，没有可搬运产物 | 增加含四项服务镜像的可导入包、无密钥配置模板、脚本、版本清单与校验文件 |
| 默认初始化政策未明确 | 合成业务数据幂等种入；样例政策通过显式初始化步骤向量化，日常启动不重复调用模型 |
| 验收不限制真实请求和失败处理 | 本次执行新增真实模型 HTTP 请求合计最多 10 次，失败也计数；离线回归优先，证据不足不宣告完成 |

## 3. 业务完成标准

| 功能 | 交付行为 |
|---|---|
| 订单/物流 | 从本地虚构订单和物流记录查询，异常识别由业务规则执行 |
| 售后政策 | 上传、处理、发布、真实 Qwen 向量检索、答复引用；只检索当前租户已发布政策 |
| 工单 | Agent 提出草稿，用户确认后真实创建；列表、详情、状态和时间线可追踪 |
| 退款 | 草稿确认→角色审批→本地演示退款入账；部分退款、全额退款、金额不足均有明确结果 |
| 库存调度 | 查询→建议→确认→审批→创建调拨单并预留源仓库存；到期释放预留。目标仓 on_hand 不在本期自动增加 |
| 权限与审计 | 身份校验、角色约束、禁止自批、租户隔离；成功与失败记录可查询 |
| Agent | 模型负责规划和回答；订单金额、库存、权限及审批由后端校验；模型文本不能直接绕过确认执行 |

退款入账是虚构数据上的真实数据库事务，不发生资金支付。库存预留是虚构数据上的真实库存状态变更，不宣称物流运输或仓库收货完成。

## 4. 架构与操作约定

- 四项容器：web、backend、postgres/pgvector、redis。独立 Compose 项目名 aftersales-local-demo；独立数据库、缓存和政策文件命名卷。
- 使用独立 infra/compose.local-demo.yaml；保持现有开发和历史验收 Compose 的语义。
- 唯一宿主机映射默认 127.0.0.1:38080，通过 DEMO_WEB_PORT 覆盖。启动前检查端口占用；有冲突时给出具体修正方式，不自动抢占或停止其他项目。
- 启动脚本定位项目根目录，兼容目录包含中文和空格；优先查 PATH 中的 Docker CLI，再查 Docker Desktop 标准安装路径，不修改全局 PATH。
- 日常启动验证 Docker Engine/Linux 容器、配置和镜像，启动后在有限时间内等待数据库、缓存、后端 readiness 和 Web 可用，成功后才显示工作台地址。健康检查不调用模型。
- 所有服务使用适合本机的资源约束与 restart: unless-stopped。自动恢复以 Docker Desktop/Engine 已启动为前提；Windows 登录时启动 Docker Desktop 由用户在其设置中开启。
- stop.ps1 停止服务并保留容器、卷；status.ps1 显示服务健康与本机地址。镜像更新通过 start.ps1 -Build 或独立构建脚本显式执行。
- 初始化数据不得覆盖已有订单金额、工单、审批或库存。政策初始化通过独立 init-demo.ps1 执行；根据文档/版本摘要判断已有结果，不重复向量化。
- 正常启动和初始化失败均返回非零退出码，保留可排查的脱敏信息，不删除卷或反复重试收费请求。

## 5. 环境与模型额度

### 环境配置

复用已有 .env，绝不覆盖其中的 Key、密码和 JWT。专用 Compose 显式启用 live,deepseek 和 local-demo 业务模式，不因 .env.example 默认 mock 而静默使用假模型。

新增演示专用配置使用独立变量名；优先以启动参数/专用模板表达，避免改变其他栈共享变量的语义。缺 .env 时沿用随机密码生成逻辑，再提示用户补充两项模型 Key；模型必需参数未配置时停止，不假装启动成功。

不打印完整 docker compose config、容器环境或 .env 内容。模板、构建上下文、镜像、前端和镜像包均不含真实 Key。Docker 管理员能检查容器环境是正常的本机权限边界，不承诺向 Docker 管理员隐藏 Key。

### 额度规则

- 旧环境默认 lifetime，保留 V5 累计预算表及已有计数。
- 新演示栈显式 daily，默认每日最多 50 次模型 HTTP 请求，范围保持 1–50；聊天、embedding、失败请求共同计数，关闭自动重试。
- 使用固定 Asia/Shanghai 时区，以服务端时钟确定日期；每日桶通过唯一约束与原子 SQL 预留，不用内存计数或启动时清零。
- 新增独立每日预算表/迁移，不改已执行的 Flyway 历史文件。跨天使用新桶，容器重启、并发请求都不能突破当天上限。
- 预算只拦截模型目标请求，不误计普通 HTTP；确认 RestClient/WebClient 路径不会双重计数。
- 耗尽时普通业务页面仍可用；模型操作返回可理解的限额提示和下一恢复时间。请求次数上限不等于人民币费用上限。
- 本次真实验收另设新增最多 10 次的硬限制，覆盖聊天、embedding、政策初始化与失败请求；这个限制不会因跨日而恢复。达到后停止真实调用并记录未覆盖项，不调高额度继续测。
- 已在对话出现过的 Key 建议长用前轮换；本次不自动替换或回显。

## 6. 执行任务、依赖与验收

依赖：计划获批。

步骤：
1. 核对当前源码、历史未完成 T9、Docker Desktop/Compose 版本、资源和现有容器；只记录相关信息。
2. 运行后端干净打包与前端锁文件生产构建；先做与 planner、审批和库存相关的既有回归，定位实际失败。

4. 对 160 条既有 mock 评估的失败和缺 fixture 分类；声明支持的核心场景必须修复，不能用删除断言或跳过 fixture 掩盖问题。

验收：当前源码能产生新 JAR 与前端产物；诊断和结果可复现。未完成项明确记录；构建失败不得使用历史旧镜像冒充新版本。

### P2：补齐演示退款与业务语义

依赖：P1 可构建；可先于 Docker 脚本实现。

步骤：
1. 增加显式 local-demo 业务模式；沿用原模拟模式供旧环境使用。
2. 新增本地退款记录，以 tenantId/actionId 唯一约束实现幂等，并关联订单。
3. 退款累计金额条件更新、退款记录、审批终态和成功审计在同一事务内完成；不同 action 并发作用于同一订单时也不能超退。
4. 部分/全额退款进度独立表达，不改变物流状态。已存在 SIMULATED_SUCCEEDED 记录可读取，不自动补执行。
5. 前端、API、评估 fixture 和演示说明同步：新结果称“演示订单退款已入账”；库存称“已预留”，不称“已到仓”。

验收：重复执行同 action 只入账一次；并发不同 action 不超退；失败事务无半条账；未批准/自批/跨租户拒绝；拒绝或过期申请不改金额；既有模拟结果仍能显示。沿用库存预留/释放功能，补必要回归。

### P4：制作专用 Compose 和镜像版本

步骤：

2. 使用最新源码构建镜像，记录镜像 tag、image ID、构建时间及排除密钥后的源码摘要。

验收：新镜像启动实际包含 P2/P3；宿主机仅有工作台回环端口；配置中无密钥输出；数据库/缓存/后端不发布宿主机端口。

### P5：一键脚本与初始化

依赖：P4。

文件：scripts/start.ps1、stop.ps1、status.ps1、init-demo.ps1、reset-demo.ps1 及共享辅助模块；New-LocalEnv.ps1 仅按需要改。

行为：
- 一条启动命令完成预检、首次构建或导入、启动、等待就绪、显示访问地址；已有匹配镜像日常启动不下载依赖或重新编译。
- 源码或包版本改变时明确提示更新方式，防止悄悄运行旧业务代码。
- 缺 Key、Docker 未启动、端口占用、健康检查超时均给出具体且脱敏的失败提示。
- init-demo.ps1 通过应用授权 API 初始化三份样例政策，发布成功后验证状态；重复执行无新增相同版本或 embedding 请求。已失败步骤支持明确续做，不无限重试。

- 登录用户名固定，密码保留在本机 .env；提示用户本地读取方式，不写入包或日志。

验收：项目根目录外调用、中文/空格路径、Docker CLI 不在 PATH、重复启动/停止、缺配置、端口占用和超时均表现正确；停止和再次启动后数据仍在。

7. 检查镜像包、前端静态资源、构建上下文和报告无凭据。检查网络绑定、SSE 与角色权限。
8. 更新执行账本、验收报告和最终操作说明；交付时列出地址、短命令、业务终点及真实模型限额。

最终门槛：当前版本构建通过；目标业务和权限用例通过；真实模型与向量检索有证据；包装启动与重启持久化通过。任何门槛失败先修复；无法完成则报告准确限制，不写“全部完成”。

## 7. 执行组织与变更控制

按项目 AGENTS.md：成规模实现由可用的 GPT-6 Luna 执行，先读取 executor-debugger；主代理负责范围、集成、最终复核。纯计划文档由主代理完成。

交接按 P2/P3 后端、P4–P6 包装分配明确文件职责和验收；相关文件有交叉时顺序执行。执行者须保留其他人的编辑，不回退无关代码。收尾使用 review-test-simplify，检查深度匹配实际变更。

顺序：P1→P2/P3→P4→P5→P6→P7。验证尽量复用既有测试；只为事务、并发、额度和脚本失败行为新增有价值的覆盖，不为文档添加测试。全量回归在最终集成后执行一次；有新失败或修改再重跑相关部分。

不提交、推送 Git 或发布公网。保留既有 .env 和验收卷。若需改变目标业务终点、模型供应商、默认每日上限或提高本次 10 次真实验收额度，先更新计划交用户审阅。
