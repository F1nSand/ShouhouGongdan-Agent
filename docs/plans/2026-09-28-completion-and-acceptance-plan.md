## T1：完整构建与环境问题处理

**步骤**

1. 记录 Java、Maven、Wrapper、Node、npm、Docker Engine 和 CLI 的实际版本及路径；检查工作区改动和现有构建脚本。
2. 捕获 Maven 错误的完整异常原因，区分路径/沙箱访问、文件占用、依赖读取和下载完整性问题；只检查相关进程和缓存文件。
3. 先采用正确路径、参数转义或合适执行环境修复。仅在确认缓存损坏时重新获取对应依赖，不删除整个 Maven 缓存；清理前确认目标位于项目构建输出目录内。
4. 执行后端 `clean package -DskipTests`，检查产物及启动入口；前端按锁文件安装依赖并执行生产构建。不以增量“无须编译”作为全量构建证据。
5. 如 Wrapper 本身有故障，修正并记录可复现命令；必要权限问题按实际工具审批处理。

**涉及文件**：根 `pom.xml`、`backend/pom.xml`、`mvnw.cmd`/`.mvn/wrapper/`、`backend/Dockerfile`、`frontend/package.json` 与锁文件；仅修改被证据证实有问题的部分。项目 `.m2` 为忽略的本地缓存。

**验收**：从干净构建输出生成 `backend/target/aftersales-agent.jar` 和 `frontend/dist`；命令、退出码和环境可复现。不存在依赖下载或清理失败被隐藏为成功。

**证据/失败处理**：保存脱敏构建摘要；失败时记录准确异常及可执行替代路径，T3 不标记完成。

## T2：模型配置绑定与 provider 检查

**步骤**

1. 以项目锁定的 Spring AI 1.1.2 依赖元数据和自动配置实现为依据，检查 chat/embedding 的 Key、base URL、model、dimensions、路径、响应格式和 extra-body 所需属性层级。尤其核对 embedding 参数是否须位于 `options` 下，避免 YAML 看似正确但未绑定。
2. 检查 `mock`、`live`、`live,deepseek` 三种模式：唯一的应用 ChatProvider/EmbeddingProvider，底层模型选择正确，DashScope 在 DeepSeek 模式不误启用。
3. 使用本地 HTTP stub 和占位 Key 检查实际发送的 URL、Authorization 所属服务、模型 ID、1024 维参数、JSON 响应解析及 thinking 配置；不连接真实服务。
4. 核对 `.env.example`、Compose 注入及知识向量模型标识与实际请求一致；解决直接 Maven 启动不自动加载 `.env` 的使用问题，必要时增加读取 `.env` 的本地启动脚本。
5. 配置与真实请求不一致时修复最小范围，并增加能捕获该配置错误的契约检查。

**涉及文件**：`backend/src/main/resources/application*.yml`、`agent/LiveChatProvider.java`、`knowledge/*EmbeddingProvider.java`、`config/EmbeddingProperties.java`、`.env.example`、`infra/compose.yaml`；拟新增 `backend/src/test/java/com/aftercare/config/ModelConfigurationIT.java` 与必要的本地启动脚本。

**验收**：实际请求分别指向预期聊天和 embedding 端点；模型 ID、维度正确；不存在重复 bean、未解析配置或凭据串用；mock 启动不需要模型 Key。模型标识用于持久化和检索过滤，值与请求一致。

**证据**：保存不含真实 Key 的绑定断言和 stub 请求断言。不要将原始环境变量或 Compose 展开配置打印到报告。

**步骤**

1. 用本地依赖 stub 模拟 401、429、超时、无效 JSON、错误向量维度和缺失证据，验证错误映射与超时/重试预算；不依赖真实服务制造故障。
2. 在独立验收栈让任务进入可观察的处理中状态后重启后端，验证运行终态、租约接管、幂等执行和审计；避免仅用未发生任务中断的正常重启代替恢复验证。
3. 重启或重建验收服务但保留卷，检查数据库记录和政策原文件可读、检索一致；验证 SSE 断线重连及 Nginx 行为。
4. 准备可复现的确定性请求脚本，记录实际数据规模；检查是否能对整个验收栈设置总计 4 CPU/8 GiB 的可验证资源约束，不能把每个服务各 4 CPU/8 GiB 称作整体基线。
5. 在明确的资源范围内预热 100 次，以 10 并发执行正式 200 次普通业务查询/确定性流程请求，记录 P50/P95、错误数、样本量和资源占用。实时模型仅测预算内案例的端到端耗时，不做无预算模型压测。
6. 分别统计首进度事件、普通 API 和最终答复耗时；实时模型样本不足时明确不代表稳定的容量结论。

**涉及文件**：`jobs/`、`agent/` 恢复/SSE逻辑、超时配置、Nginx、拟新增 `infra/compose.acceptance.yaml` 与 `scripts/Measure-Acceptance.*`、必要故障验证脚本。
