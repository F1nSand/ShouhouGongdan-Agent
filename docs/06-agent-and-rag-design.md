# Agent 编排与政策 RAG 设计

## 运行目标与上下文

Agent 将自然语言需求转换为有限的查询和草稿生成步骤。每次运行绑定不可变身份、商家、会话、runId、traceId、截止时间与工具预算。

首期支持 ORDER_QUERY、LOGISTICS_EXCEPTION、POLICY_QA、TICKET_DRAFT、INVENTORY_QUERY、TRANSFER_RECOMMENDATION、SENSITIVE_ACTION_DRAFT、UNKNOWN 八类意图。分类只决定候选工具，不产生执行权限。

模型接收最近 10 条消息和最多 6000 字的会话摘要；摘要通过模型上下文生成只用于理解问题，订单事实和库存始终重新查询。敏感操作参数不从摘要直接执行。

当前首期实现不把业务记录发给模型生成事实。mock provider 根据输入作确定性意图识别；live provider 通过 Spring AI ChatClient 调用 DashScope，只返回固定枚举意图及受长度约束的字段。后端将意图映射到服务器注册的 `ToolGateway`，最终答复由领域查询结果和已检索证据组装。

## 运行流程

1. 认证、会话权限和请求去重检查，建立 agent_runs。
2. 限流与预算检查，模型识别目标；后端将意图映射为白名单工具。
3. 缺订单号、SKU 或目标仓时提问，不猜测业务 ID。
4. 查询领域服务，校验每次工具入参、输出和身份范围。
5. 需要政策解释时检索证据，结合订单事实生成结构化回答。
6. 需要操作时创建 PREPARING 草稿，保存服务器验证过的参数和摘要。
7. 验证引用与数字，保存消息、引用和草稿证据快照，将草稿转 READY，再输出答复与草稿可见事件；失败草稿转 INVALIDATED。
8. 无草稿转 COMPLETED；有草稿转 WAITING_CONFIRMATION。
9. 用户确认后由命令服务执行工单创建或提交待审批申请；同一事务将结果消息和 `action.result` 事件追加到原会话。

## 回答契约

~~~text
AssistantAnswer {
  answer: string
  citations: [{chunkId, quote}]
  suggestedActions: [{draftId, type, summary}]
  needsHuman: boolean
  reasonCode: string | null
}
~~~

后端必须验证 citations.chunkId 属于本次检索证据，quote 为片段中的真实文字，订单金额、库存数量与建议事实一致。当前首期由服务器确定性组装事实答复，并在保存或流式发送前调用 CitationValidator；无效引用不会进入消息或 SSE。结构修复及其预算在后续引入模型生成最终答复时启用。

用户界面展示依据与操作摘要，不展示模型内部推理。

## 工具约束与预算

单轮最多 6 次模型调用、8 次工具调用，包含重试。整轮自动处理最长 60 秒，模型单次超时 20 秒，只读工具 5 秒，数据库查询 3 秒。所有子步骤受剩余整轮时间限制，不重新延长期限。首期每轮执行一次模型意图识别；重试仍计入相同预算。

结构修复也消耗模型预算。只读网络超时最多重试一次，退避 250 ms；权限失败、参数错误和无数据不重试。草稿持久化采用调用 ID 去重，不在失败后盲目复制草稿。

剩余预算耗尽时停止调用，说明已完成的查询、未完成事项与可选手工入口。禁止循环调用同一工具和同一输入来重复获取相同结果。

## 知识导入

~~~mermaid
flowchart LR
    F[上传文件与有效期] --> V[校验大小、类型与哈希]
    V --> J[持久化导入任务]
    J --> P[PDFBox / 文本解析]
    P --> C[分段与定位]
    C --> E[Embedding]
    E --> D[pgvector 入库]
    D --> READY[READY 预览]
    READY --> PUB[管理员发布]
~~~

首期文本按段落优先切分，每段目标 500 个 Unicode 字符，最大 800，重叠 100；保留页码或章节、片段顺序和文档版本。长段落按句子切分，无法分句时按字符边界分割。

单个片段内容、模型标识和维度入库。向量长度不是 1024 时拒绝整个版本发布；不可静默截断或填充。Embedding 批量请求大小按模型限制和配置控制，失败批次以版本 ID+chunkIndex 幂等重试。

内容处理异常转 FAILED，保存错误码与可读原因。修复后创建新处理任务，重复执行先检查已经入库的片段哈希。未经发布的内容不参与回答。

## 检索流程

1. 用订单号关联订单，policyReferenceTime 取 purchased_at；没有订单时取当前时间。
2. 构造 tenantId、categoryCode、文档 ACTIVE、版本 PUBLISHED、当前 embeddingModel、effectiveFrom ≤ referenceTime < effectiveTo 的过滤；effectiveTo 为空表示无上限。
3. 为问题生成同模型、同维度 query vector。
4. 采用 pgvector 余弦检索，候选最多 20，最终最多 8。
5. 初始最低相似度设为 0.65，在固定评测集上校准后记录配置与结果；不把该阈值当作事实正确性的证明。
6. 检查候选是否有冲突或缺关键条件，向模型提供带受控 chunkId 的内容。
7. 保存实际使用引用的文档标题、版本、有效期、定位和文字快照。

首期不要求重排模型或中文全文检索插件。第二阶段可以在基准集证明收益后增加关键词检索、融合排序和重排。

## 日期与版本

政策有效期左闭右开。文档的新版本发布时按生效边界结束旧版本，而不是删除旧文字；历史订单可检索购买当时的政策。

同一文档的版本区间不重叠。不同政策文档对同问题给出冲突结论时不让模型自行选定一方，答复列出冲突和引用并转人工。

管理员撤回版本后标为 ARCHIVED，不用于后续检索；已经保存的回答引用显示“此版本已停用”，仍保留当时的证据。

## 流式交互

工具进度即时通过 SSE 输出。业务回答先形成结构化内容并校验引用与数字，再把已通过校验的答案分段发送 answer.delta 和 answer.final。

首期不把未经校验的模型原始 token 直接作为最终政策答复推送。用户先看到“查询订单”“检索政策”等真实进度，随后看到校验后的答案。评测分别计算首个进度事件和最终答案延迟。

## 注入与数据最小化

用户输入、政策文本、工具返回均视为数据，不能覆盖系统规则。文件中“忽略权限”“批准退款”等指令不产生执行资格；真正写操作没有模型可调用的审批工具。

给模型的订单仅包含处理问题所需字段。手机号、地址、访问令牌等从工具结果中剔除或脱敏。检索不能接受模型生成的任意 SQL、文件路径或网络 URL。

工具白名单只包含订单、物流、政策、库存查询、调拨建议和两种草稿。工具参数不接受 `tenantId`、`actorId`、角色或 traceId；工具身份始终来自当前认证上下文。确认、审批、退款执行和库存预留命令不注册为模型工具。

模型与 Embedding 超时可降级为业务信息展示及手工工单流程；知识检索失败时不以模型记忆回答商家政策。

## 场景示例

- 订单不存在：返回未查到，不查询其他商家或编造物流。
- 物流超时但缺退款政策：说明物流异常事实，生成售后沟通建议，退款资格转人工。
- 当前库存不够：输出查询数量与原因，不生成可执行调拨方案。
- 用户要求立即退款：展示政策依据和审批草稿，确认后进入待审批。
- 政策文本包含越权指令：保留政策事实，任何敏感动作仍通过确认和审批服务。
